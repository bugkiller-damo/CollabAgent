## 1. 评审背景与目标

### 1.1 当前状态

CollabAgent 是一个 **AI 原生团队协作平台**，核心能力是人与 AI Agent 通过频道/私信进行实时协作。Agent 由本地 daemon（Claude CLI 子进程）驱动。

### 1.2 目标状态

转型为 **三级智能体安全渗透测试平台**，支撑集团-子公司两级监管架构：

```
监管层（集团）  ─── 集团中枢智能体 + 监管看板 + 集团病例库
     │                    │
通信层（协作平台）─── 消息驱动的智能体沟通枢纽
     │                    │
管理层（子公司）─── 子公司智能体 + 任务/资产/病例管理
     │                    │
执行层（渗透引擎）─── 外部安全公司 API 接口（渗透测试业务）
```

### 1.3 转换原则

| 原则 | 说明 |
|---|---|
| **最大化复用** | 当前 CollabAgent 的频道/消息/WS/Auth/管理后台等核心资产直接继承 |
| **分层隔离** | 四层职责严格分离，渗透执行层隔离在平台之外（通过 API 对接） |
| **多租户优先** | 从架构第一天就设计为支持多集团/多子公司的数据隔离 |
| **离线自治** | 子公司层支持断网后按本地策略继续运行 |
| **渐进式迁移** | 不重写，采用重构 + 扩展的方式，每个迭代可独立交付 |

## 2. 现有架构分析

### 2.1 包结构现状

```
collabagent/                    pnpm monorepo
├── packages/
│   ├── shared/                 纯 TypeScript 类型定义（Message/Channel/Agent/WS 协议）
│   ├── server/                 Fastify 5 后端（~17 条路由 + WS）
│   ├── web/                    React 19 前端（~15 个页面 + 7 个 Zustand Store）
│   └── daemon/                 Claude CLI 子进程驱动（常驻/一次性模式）
└── docs/                       文档
```

### 2.2 核心能力盘点

| 能力 | 实现程度 | 评估 |
|---|---|---|
| 频道/消息/线程 CRUD | ✅ 完整 | 可直接复用 |
| WebSocket 实时双向通信 | ✅ 完整 | 需扩展 ACK/离线缓存 |
| @提及与自动入频道 | ✅ 完整 | 可直接复用 |
| DM（私信） | ✅ 完整 | 需扩展 group_dm |
| 用户认证（JWT/bcrypt） | ✅ 完整 | 需加 OAuth 2.0 层 |
| CSRF 防护 | ✅ 完整 | 可直接复用 |
| 角色/权限 | ⚠️ 基础（owner/admin/member） | 需扩展 RBAC |
| 多级组织 | ❌ 无（仅 servers 表） | 需新建 |
| 任务看板 | ✅ 基本 | 可演变为渗透任务管理 |
| 提醒系统 | ✅ 完整 | 可演变为告警规则引擎 |
| 文件上传/附件 | ✅ 完整（本地磁盘存储） | 可选扩展对象存储 |
| 指标/监控 | ⚠️ 基础（进程级计数器） | 需扩展告警引擎 |
| 管理后台 | ✅ 多页管理 | 可直接复用结构 |
| 第三方集成 | ❌ stub | 需完整重写适配器层 |
| 搜索 | ⚠️ 仅英文 to_tsvector('simple') | 需加中文分词 |
| 通知 | ❌ 无 | 需新建 |

### 2.3 关键架构债务

| 债务 | 说明 |
|---|---|
| `server/index.ts` 约 450 行 | 路由与内联逻辑混合，需按模块拆分 |
| `daemon` 直接写死 windows 路径 | 跨平台受限（暂维持现状） |
| 前端 bundle 未 code-split | ~690KB 单 chunk |
| 无统一 API 版本管理 | 所有路由平铺在 `/api/*` |
| JWT 存 localStorage | XSS 风险（过渡方案） |

### 3.3 分阶段拆分策略

为避免一次性重构过大，采用 **同库包拆分 → 渐进独立化** 策略：

| 阶段 | 动作 | 代码变化 |
|---|---|---|
| **Phase 0** | 当前 monorepo，所有新代码在现有 server/web 中添加 | 零结构变化 |
| **Phase 1** | 创建 adapter-layer 新包 + penetration-gateway 新包 | 新增 2 个包 |
| **Phase 2** | server 按域拆为多文件（routes/v1/、db/schema/） | 内部重构 |
| **Phase 3** | web 按业务拆为 collaboration/ + security/ 目录 | 内部重构 |
| **Phase 4** | 安全业务可行性成熟后，可选独立部署 | 拆分 |
| **Phase 5** | platform 服务稳定后，可选拆为独立进程 | 拆分 |

### 5.3 核心 ER 关系

```
集团 (server type=group)
  │
  ├── 子公司 A (server type=subsidiary, parent_id=集团)
  │     ├── 用户 (users ← server_members)
  │     ├── Agent (agents ← server_id)
  │     ├── 资产 (assets ← subsidiary_id)
  │     ├── 渗透任务 (penetration_tasks ← subsidiary_id)
  │     │     ├── 渗透结果 (penetration_results ← task_id)
  │     │     └── 攻击图 (attack_graphs ← task_id)
  │     ├── 本地病例 (cases ← subsidiary_id)
  │     ├── 告警规则 (alert_rules ← subsidiary_id)
  │     │     └── 告警 (alerts ← rule_id)
  │     └── 审计日志 (audit_logs ← subsidiary_id)
  │
  └── 集团病例库 (cases WHERE status='published')
```

### 6.3 OAuth 2.0 认证流设计

```
场景 A：平台 Web 登录（Auth Code + PKCE）
  用户浏览器 → 登录页 → 授权 → 回调 → access_token + refresh_token

场景 B：服务间调用（Client Credentials）
  安全公司/适配器 → POST /api/v1/oauth/token
    { client_id, client_secret, grant_type: "client_credentials" }
    → { access_token, expires_in }

场景 C：daemon 本地 Agent（保留现有机器令牌）
  sk_machine_ 令牌不变，仅在平台内部流转
  未来可平滑迁移到 OAuth Device Grant
```

### 6.4 限流策略

| 限流对象 | 默认阈值 | 处理 |
|---|---|---|
| 单 IP（渗透引擎 API） | 100 次/分钟 | HTTP 429 + Retry-After |
| 单 API Key | 1000 次/分钟 | HTTP 429，连续 3 次临时禁用 15min |
| 单用户（控制台 API） | 300 次/分钟 | HTTP 429 |
| WS 单连接 | 200 条消息/分钟 | 丢弃消息 + 限流通知 |
| 全局（集团平台） | 5000 次/分钟 | HTTP 429 + 扩容告警 |

## 7. 通信协议设计

### 7.1 双平面通信架构

```
主通道（协作平台）              兜底通道（API 直连）
    │                              │
    │ WebSocket + REST              │ HTTP REST
    │ 支持人机交互                  │ 仅智能体间
    │ 消息持久化                    │ 确保关键数据可靠传递
    │ 实时广播                      │ 策略/病例/指令
    │                              │
    └──────────┬───────────────────┘
               │ 冲突检测
               │ 默认以 API 直连为准
               ▼
         审计日志（记录冲突处理全过程）
```

**冲突处理策略**：
- 每条消息携带序列号 `{sender_id}:{seq_num}`
- 两通道独立维护序列号空间
- 协作平台恢复后比对最近 1 小时数据
- 高序列号覆盖低序列号
- 冲突处理全程记录审计日志（含 SHA-256）

### 7.2 WS 协议增强

当前消息类型保留，新增：

| 消息类型 | 说明 | 方向 |
|---|---|---|
| `ack` | 消息确认（含 status：received/processed/rejected） | 双向 |
| `policy_publish` | 监管策略发布 | 中枢 → 子公司 |
| `global_command` | 全局指令下发 | 中枢 → 子公司 |
| `vulnerability_alert` | 高危漏洞告警 | 子公司 → 中枢 |
| `case_notify` | 病例分发通知 | 中枢 → 子公司 |
| `coordination_req` | 跨域协调请求 | 双向 |
| `status_change` | 智能体在线状态变更 | 双向 |
| `mention_notify` | @提及通知 | 平台 → 接收方 |

### 7.3 消息确认机制

```
HIGH/CRITICAL 消息要求 ACK
- 默认 ACK 超时：10s
- HIGH：5s
- CRITICAL：3s
- 重试：指数退避（1s→2s→4s），最多 3 次
- 连续失败 → 标记 offline
```

### 7.4 在线状态管理

| 状态 | 定义 | 转换 |
|---|---|---|
| `online` | WS 连接已建立并鉴权 | WS open → online |
| `offline` | WS 断开 > 30s | 心跳超时 → offline |
| `busy` | 正在处理密集型任务 | 可选 DND 标记 |

状态变更通过 WS 广播 `status_change`，daemon 每 15s 发送心跳。

## 8. 安全架构设计

### 8.1 多层安全模型

| 层 | 安全机制 | 说明 |
|---|---|---|
| **传输层** | TLS 1.3 强制 | 所有外部通信加密 |
| **认证层** | OAuth 2.0 + JWT + 机器令牌 | 三模认证，按场景选择 |
| **授权层** | RBAC 角色矩阵 | 6 种预置角色，操作级权限 |
| **审计层** | 完整审计日志 | 所有改写操作记录 |
| **数据层** | Row-Level Security + 行级隔离 | 子公司间严格隔离 |
| **API 层** | 限流 + 签名验证 + CSRF | 防滥用、防伪造 |

### 8.2 RBAC 角色矩阵

| 角色 | 资产管理 | 任务管理 | 病例 | 配置 | 用户 | 审计 |
|---|---|---|---|---|---|---|
| 系统管理员 | CRUD | CRUD | CRUD | CRUD | CRUD | 读 |
| 安全分析师 | 读 | 读 | 读 | - | - | 读 |
| 渗透测试员 | 读 | CRUD | 读 | - | - | - |
| 审批管理员 | 读 | 读 | 审批 | - | - | - |
| 审计员 | - | - | - | - | - | 读 |
| 子公司管理员 | 本公司 | 本公司 | 本公司 | 本公司 | 本公司 | 本公司 |

### 8.3 密码与账户策略

| 策略 | 要求 |
|---|---|
| 密码最小长度 | 12 字符 |
| 复杂度 | 大写 + 小写 + 数字 + 特殊字符（至少 3 类） |
| 有效期 | 最长 90 天 |
| 历史 | 禁止最近 5 次 |
| 锁定 | 连续 5 次失败锁定 30 分钟 |
| 会话超时 | Web 30 分钟自动登出 |
| MFA | 管理员角色强制（TOTP / WebAuthn） |

## 10. 风险与权衡

### 10.1 技术风险

| 风险 | 概率 | 影响 | 缓解措施 |
|---|---|---|---|
| 多租户迁移导致现有数据不兼容 | 中 | 高 | 先写回滚脚本，staging 环境完整测试 |
| WS 协议增强破坏现有 daemon 连接 | 中 | 高 | 扩展而非修改现有消息类型，向下兼容 |
| 适配器层过度工程 | 中 | 中 | 先实现 1-2 个具体适配器再抽象接口 |
| API 网关成为性能瓶颈 | 低 | 中 | 网关设计为无状态，可水平扩展 |
| 第三方安全公司 API 不稳定 | 高 | 中 | 适配器层实现统一错误处理 + 降级策略 |

### 10.2 设计决策记录

| 决策 | 选项 | 选择 | 理由 |
|---|---|---|---|
| 同库 vs 拆分独立包 | 渐进重构 vs 新仓库 | **渐进同库** | 避免 git 历史断裂，团队不需要切换上下文 |
| 渗透引擎 API 网关位置 | 平台内置 vs 独立服务 | **独立包但同仓库** | 渗透接口有独立的安全要求，前期同仓库便于联调 |
| 病例库存储 | PostgreSQL 原生 vs ES | **PostgreSQL + pgvector** | 运维复杂度最低，搜索量达百万级再考虑 ES |
| 离线消息队列 | 内存 vs Redis vs Kafka | **Redis Streams** | ioredis 已在依赖中，零新增运维成本 |
| RBAC 实现 | 硬编码 vs 配置驱动 | **预置角色 + 可扩展** | 需求明确定义 6 种角色，先硬编码 |
