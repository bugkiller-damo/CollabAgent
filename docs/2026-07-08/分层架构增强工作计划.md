## 1. 现状评估

### 1.1 数据层 ✅ 已就位

`servers` 表已支持两级组织（`type` + `parent_id`），所有 v1 API 都通过 `subsidiaryId` 隔离数据，**架构正确**。

### 1.2 代码层 ⚠️ 关键缺失

| 监管层（集团中枢） | 管理层（子公司智能体） |
|---|---|
| ❌ 无集团仪表盘 API | ✓ 当前 v1 路由已就绪 |
| ❌ 无跨子公司聚合查询 | ✓ resolveUserContext 已实现 |
| ❌ 无子公司列表/详情页 | ⚠️ 但只在单 subsidiary 视角 |
| ❌ 无全局策略下发端点 | ⚠️ broadcastToDaemons 已存在但未使用 |

### 1.3 前端层 ❌ 空白

| 现有 | 缺失 |
|---|---|
| `/security/assets`（子公司视角） | `/group/dashboard`（集团 KPI） |
| `/security/tasks`（子公司视角） | `/group/subsidiaries`（子公司列表） |
| `/security/cases`（子公司视角） | 顶部子公司上下文切换器 |
| `/security/alerts`（子公司视角） | `/group/policies`（策略下发） |

### 1.4 当前数据流 vs 目标数据流

```
当前（单层）                  目标（分层）
                          ┌─ 集团中枢（监管）
                          ├─ 中央策略 → 子公司
用户 → v1 API → 单 DB       ├─ 全局 KPI 聚合
                          ├─ 跨子公司病例库
                          └─ 子公司 A/B/C（执行）
                            └─ 每个子公司有独立 v1 数据
```

## 2. 目标架构

### 2.1 角色与权限矩阵

| 角色 | 可见范围 | 操作权限 |
|---|---|---|
| `system_admin`（集团） | 所有子公司 + 全局视图 | 全局策略下发、子公司管理、病例审核 |
| `subsidiary_admin`（子公司） | 仅本公司数据 | 创建任务、审核本地病例、管理本地资产 |
| `pen_tester` | 仅本公司数据 | 创建/查看任务 |
| `auditor` | 仅审计日志 | 只读 |

### 2.2 上下文切换器（关键 UX）

```
┌──────────────────────────────────────────────────┐
│  顶部栏：当前角色：集团中枢  │  当前视角：子公司 A ▾  │
└──────────────────────────────────────────────────┘
```

集团管理员可通过下拉切换"以子公司 A 视角"或"全局视角"，类似 GitHub 的组织切换。

## 3. API 设计清单

### 3.1 集团监管 API（新增 5 个端点）

```
GET    /api/v1/group/dashboard
       返回：总子公司数 / 总任务数 / 总漏洞数 / 集团病例库 / 最近活动 / Top10 子公司排名

GET    /api/v1/group/subsidiaries
       返回：所有子公司列表 + 每个子公司状态（在线/离线/agent 数/最近活跃）

GET    /api/v1/group/subsidiaries/:id
       返回：单个子公司详细信息（资产/任务/病例统计）

GET    /api/v1/group/vulnerabilities
       返回：跨子公司漏洞聚合（按 CVE/CVSS 分组，含受影响子公司数）

POST   /api/v1/group/policies
       body: { policyType, value, targetSubsidiaryIds }
       下发全局监管策略（如扫描间隔、熔断阈值）
```

### 3.2 上下文切换 API（新增 2 个端点）

```
POST   /api/v1/auth/switch-context
       body: { subsidiaryId?: null=全局视角, subsidiaryId="xxx"=以子公司视角 }
       返回：新的 short-lived token + effective subsidiaryId

GET    /api/v1/auth/current-context
       返回：当前有效角色 + 视角 + subsidiaryId（用于前端展示）
```

### 3.3 数据模型新增（无需新表，复用现有字段）

`servers` 表已有 `type/parent_id/level/config`，新增 `config` JSON 字段中支持以下结构：

```json
{
  "scanStrategy": {"interval": "4h", "intensity": "standard"},
  "securityControl": {"forbiddenOperations": ["dos"], "circuitBreakerLatencyMs": 2000},
  "caseDistribution": {"pushMatchThreshold": 0.6}
}
```

## 4. 前端结构规划

### 4.1 路由扩展

```
/security/...               现有：子公司视角
/group/dashboard            新增：集团 KPI 仪表盘

/group/vulnerabilities      新增：跨子公司漏洞聚合
```

### 4.2 顶部上下文切换器组件

`<GroupContextSwitcher />` 放置于 `<AppLayout />` 顶部，仅当用户角色为集团级（system_admin）时显示：

```tsx
{role === 'system_admin' && (
  <div className="flex items-center gap-2 border-b bg-blue-50 dark:bg-blue-900/20 px-4 py-2">
    <span className="text-xs">监管视角：</span>
    <select value={currentSubsidiaryId ?? '__global__'} onChange={...}>
      <option value="__global__">🌐 全局视角（监管层）</option>
      {subsidiaries.map(s => <option key={s.id} value={s.id}>子公司 {s.name}</option>)}
    </select>
  </div>
)}
```

### 4.3 安全业务页面扩展

所有 `/security/*` 页面在检测到 `contextMode === 'global'` 时，自动切换为：
- 标题加 "🌐 全局" 前缀
- 显示数据范围选择器
- 操作按钮变 "查看子公司详情"（不可直接修改）

### 6.2 关键决策点

| 决策 | 选项 | 推荐 |
|---|---|---|
| 上下文切换机制 | URL query 参数 vs 切换 token | **切换 token**（更清晰，权限隔离好） |
| 集团仪表盘刷新频率 | 手动 vs 5s 自动 | **手动刷新**（数据量大，避免不必要负载） |
| 策略下发形式 | 广播 vs 轮询 | **WS 广播**（已有基础设施） |
| 跨子公司数据隔离 | RLS vs 应用层 | **应用层过滤**（保持架构一致性） |

### 6.3 风险评估

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 上下文切换导致权限提升漏洞 | 高 | 严格校验切换请求的角色权限 |
| 集团聚合查询性能 | 中 | 限制查询范围 + 加索引 + 缓存 KPI |
| 跨子公司数据可见性边界 | 中 | 字段级 RBAC + 审计日志 |

## 附录 A：上下文切换器状态机

```
[默认登录]
  role=system_admin → effectiveSubsidiaryId=null (全局视角)
  role=其他        → effectiveSubsidiaryId=用户个人子公司

[切换] POST /switch-context { subsidiaryId }
  if role !== system_admin:
    拒绝（403）
  else:
    生成新 JWT (role + new effectiveSubsidiaryId)
  返回新 token + sets cookie

[请求] GET /api/v1/tasks
  读取 req.user.effectiveSubsidiaryId
  if null: WHERE 1=1（返回所有）
  else: WHERE subsidiary_id = effectiveSubsidiaryId
```
