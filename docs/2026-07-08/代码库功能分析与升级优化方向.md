## 一、项目概述

**CollabAgent** 是一个 AI 原生团队协作平台，核心理念是"Agent 即队友，而非工具"。用户可以通过 Web 界面与 AI Agent 在同一频道中协作，Agent 由本地运行的 daemon 进程驱动（调用本机 Claude CLI）。

| 项目属性 | 值 |
|---|---|
| 架构 | pnpm monorepo |
| 包数量 | 4 (`shared` / `server` / `web` / `daemon`) |
| 后端 | Fastify 5 + PostgreSQL + Drizzle ORM |
| 前端 | React 19 + Vite 6 + TailwindCSS 3 + Zustand |
| Agent 驱动 | Node.js → WebSocket → Claude CLI 子进程 |
| 开发语言 | TypeScript 全栈 |
| Node 版本 | >= 20 |
| 包管理器 | pnpm >= 9 |

## 三、各模块功能详析

### 3.1 共享层（`packages/shared`）

纯类型定义，作为所有包之间的契约。定义了：
- **实体类型**：`Message`, `Channel`, `User`, `Agent`, `Task`, `Reminder`, `Attachment`
- **协议类型**：`WsServerMessage`, `WsClientMessage`（8 种服务端消息类型、5 种客户端消息类型）
- **API 响应**：`ApiResponse<T>` = `ApiOk<T> | ApiError` 范式

### 3.2 后端服务（`packages/server`）

#### 认证与安全
| 机制 | 实现 | 状态 |
|---|---|---|
| JWT Bearer | 前端 localStorage 存取 Bearer token | ✅ 使用中（过渡方案） |
| httpOnly Cookie | 同时签发 access_token cookie | ✅ 实现 |
| CSRF 保护 | Double-submit cookie 模式，改写型方法校验 x-csrf-token | ✅ 实现 |
| 机器令牌 | `sk_machine_` 前缀 + bcrypt 比对，daemon 专用 | ✅ 实现 |
| 开发令牌 | `dev-token` 快捷认证 | ✅ 实现 |
| 密码强度校验 | 前端密码强度指示器 | ✅ 实现 |
| 刷新令牌 | `/api/auth/refresh` | ✅ 实现 |
| 忘记/重置密码 | 令牌式密码重置流程 | ✅ 实现 |

#### WebSocket 层
- **双重连接管理**：浏览器客户端（按 userId 分组）+ daemon 连接（一对一）
- **频道定向广播**：公开频道全员推送；私有频道/DM 仅推送成员
- **daemon 元数据**：握手 `ready` 上报主机名/版本/运行时，用于仪表盘
- **早到消息缓冲**：daemon 在异步鉴权完成前发的消息被缓冲，注册后回放

#### 数据库设计（11 张表）

```
users ──┬── servers ──┬── channels ──── messages ──── message_reactions
        │             │       │             │
        │             │       ├── channel_members
        │             │       └── attachments (← message_attachments 关联)
        │             │
        │             ├── agents ──────── reminders
        │             │
        │             ├── machine_tokens
        │             ├── invites
        │             └── server_members
```

- `messages` 表有 `seq`（全局递增）和全文索引 `idx_messages_channel_seq`

- `reminders` 支持重复规则（`repeat_rule` 如 `every:15m`、`daily@09:00`）

### 3.4 Daemon 守护进程（`packages/daemon`）

#### 核心工作流

1. **启动** → 预检 Claude CLI → 创建 `.slock/` 工作目录 → 打包 CLI → WS 连接
2. **WS 连接** → 发送 `ready`（主机名/版本/能力） → 等待指令
3. **消息处理**（4 种场景）：
   - `agent:start` → 注册到路由表，准备响应 @提及
   - `agent:deliver` → 检测 @mentions → 路由到对应 agent
   - `agent:stop` → 从路由表注销，关闭对应 PersistentClaude 进程
   - `reminder.fire` → 唤醒 agent 做跟进
4. **Agent 执行**（两种模式）：
   - **常驻模式**（默认）：`PersistentClaude` 进程保持温热，流式 JSON 通信
   - **一次性模式**（`SLOCK_PERSISTENT_CLAUDE=0`）：每次用 `--print` 一次执行

#### Supervisor 监督进程
- 开发模式文件变更自动重启（300ms 防抖）
- 崩溃自动重启（1 分钟内 >5 次则退避到 30s）
- 干净关闭信号处理

#### slock CLI
- 基于 Commander 的命令行工具
- 支持命令：`message send`, `message list`, `tasks list`, `tasks update`, `server info`, `channel members`
- 通过 esbuild 打包为单文件，启动更快
- 生成 `slock.bat` Windows 包装器

## 四、数据流分析

### 4.1 消息发送流程（用户 → 频道）

```
用户输入 → React MessageRow
  → POST /api/messages/send (REST)
    → PostgreSQL INSERT
    → broadcast() via WebSocket
      → 浏览器客户端（同频道成员）
      → daemon 客户端（检测 @mention → 唤醒 Agent）
```

### 4.2 Agent 响应流程

```
daemon WS 收到 agent:deliver
  → mentionedAgentNames() 检测 @提及
  → resolveAgentId() 查找 agent UUID
  → runAgent() → dispatchToAgent()
    → writeAgentPrompt() 写系统提示
    → PersistentClaude.send() 入队
      → Claude subprocess 处理
        → slock message send --target "#channel" (REST)
          → POST /api/messages/send
            → broadcast() 推送到所有客户端
```

### 4.3 DM 流程

```
用户发起私信 → navigate(/dm/@peer)
  → GET /api/channels/dms (列出已有会话)
  → POST /api/messages/send?target=dm:@peer
    → resolveDmTarget() 确定性频道名
    → 广播带 dmAgentRecipients 字段
    → daemon 收到后无需 @ 也唤醒指定 agent
```

### 4.4 任务数据流

```
消息含 task fields → 自动识别为任务
  → TaskBoard 拉取 GET /api/tasks
  → 状态更新 PATCH /api/tasks/:number
  → 指派 PUT /api/tasks/:number/assign
```

### 4.5 提醒流程

```
创建提醒 → POST /api/reminders
  → reminder-scheduler 每 15s 轮询 DB
  → 到期提醒 → WS push → daemon
    → runAgentReminder() → 唤醒 agent
```

## 五、当前技术债务与风险项

### 5.1 安全风险

| 问题 | 位置 | 风险 | 建议 |
|---|---|---|---|
| JWT 存 localStorage | 前端 authStore / http header | XSS 可窃取令牌 | 改为纯 httpOnly cookie（已有 cookie 实现，但 Bearer 仍可用） |
| 邀请链接可枚举 | `GET /api/invites/:token` 无认证 | 24 字节随机 token，无限流枚举 | 加端点限流 / 绑定邮箱 |
| `dev-secret-change-in-production` | JWT_SECRET 默认值 | 生产环境未设环境变量即用弱密钥 | 加启动时必填校验 |
| docker-compose 失效 | `schema.sql` 已改名 | 容器化路径阻塞 | 修 compose 即可恢复 |

### 5.2 功能缺口

| 缺口 | 影响 | 复杂度 |
|---|---|---|
| 通知中心 | 多用户无消息聚合/红点推送 | 🟢 中 |
| 中文搜索 | `to_tsvector('simple')` 中文命中率 0 | 🟢 小 |
| Daemon npm 发布 | 接入需先 clone 仓库，非真正一行命令 | 🟢 中 |
| Metrics 持久化 | sparkline 刷新即重置，无可观测历史 | 🟡 中 |
| 卡死回合 kill | 超时仅跳过不 kill，可能错配队列 | 🟢 小 |
| stdout 缓冲无上限 | 无限增长 | 🟢 极小 |
| 运行时死选项 | runtime 下拉含 codex/deepseek 但未实现 | 🟢 极小 |

### 5.3 代码维护性

| 观察 | 位置 |
|---|---|
| `index.ts` 过长（~450 行），路由与内联逻辑混合 | `packages/server/src/index.ts` |

## 六、后续升级优化方向

### 🟢 P1 — 贴近协作体验的功能（性价比最高）

#### 1. 通知中心
- **现状**：仅频道未读数，无 @我/被指派任务/DM 的聚合与红点
- **切入点**：
  - 新建 `notifications` 表（type、actor、target、read_at）
  - 后端在消息发送/任务指派/提醒触发时写入通知
  - WS 推送新通知到浏览器
  - 侧栏加铃铛图标 + 下拉通知列表
- **参考实现**：`reminder-scheduler.ts` 的轮询模式可复用

#### 2. 纯 httpOnly Cookie 硬化
- **现状**：前端同时在 header 和 cookie 发 JWT，localStorage 存一份
- **目标**：去掉 Bearer header 模式，全走 httpOnly cookie，真正防 XSS 窃 token
- **改动范围**：
  - 前端 `authStore` / `api client` 不再读写 localStorage token
  - 后端保留 cookie 解析逻辑（已有），移除 Bearer fallback
  - **注意**：需强制所有用户重登一次

#### 3. 中文搜索分词
- **现状**：`to_tsvector('simple')` 对中文无效（不分词，命中 0）
- **切入点**：接 `pg_jieba`（轻量）或 `zhparser`（需编译）
- **涉及修复**：`messages.ts` 的 search 路由的 SQL 查询

#### 4. DM 群组 / 多人私聊
- **现状**：DM 固定两人
- **扩展方向**：扩展 `channels type='dm'` 成员模型，支持 3+ 人私聊群组

#### 5. Action Cards 闭环
- **现状**：表已建、路由仅 `prepare` 雏形
- **补全**：补"人点击提交、以人身份执行"环节（建频道/建 Agent 快捷提交）

### 🟢 P2 — 工程成熟度 / 可运维

#### 6. Daemon npm 包发布
- **现状**：接入命令为 `pnpm --filter @collabagent/daemon dev -- --server-url ...`
- **目标**：发布为 `@collabagent/daemon` 后，一行命令 `npx @collabagent/daemon ...`
- **改动范围**：`ConnectWizard.tsx` 的 command 模板，daemon package.json 的 bin 字段已有

#### 7. 邀请链接安全加固
- **现状**：24 字节随机 token，可选过期/次数，端点为公有无认证
- **增强方案**：
  - 加端点限流（每 IP 每分钟最多 N 次校验）
  - 支持绑定邮箱（邀请时输入目标邮箱，注册时校验）
  - 注册二次校验（填邀请码）

#### 8. Metrics 时序持久化
- **现状**：仪表盘 sparkline 为客户端采样，刷新即重置
- **方案 A**：服务端环形内存缓冲（最后 N 个采样点）
- **方案 B**：接 Prometheus 客户端库（推荐，长期更优）

#### 9. 多实例水平扩展
- **现状**：登录限流为内存态；WS 单进程广播
- **基础建设**：Redis（限流 `ioredis` 已依赖 + pub/sub 广播）
- **现状**：调度器已并发安全

#### 10. 频道 join/leave 服务端实现
- **现状**：靠 @提及自动入频道兜底，agent 无法主动退频道
- **切入点**：复用现有逻辑加 agent 鉴权层

### 🟢 P3 — Daemon 运行时健壮性

#### 11. 卡死回合应 kill 进程
- **现状**：`PersistentClaude` turn 超时只 `busy=false` 继续下一条
- **风险**：迟到的 result 会与后续回合错配队列
- **修复**：超时后 `kill()` 进程 → `cleanup()` → 等待重启后 `pump()`

#### 12. stdout 缓冲上限保护
- **现状**：`PersistentClaude.buf` 无换行时无限增长
- **修复**：加最大长度限制（如 1MB），超限则丢弃并打印警告

#### 13. Supervisor 识别鉴权失败码
- **现状**：daemon 鉴权失败 exit(1)，supervisor 仍按崩溃重启（退避到 30s 循环）
- **增强**：识别特定退出码后彻底停重启

#### 14. Agent 运行时死选项
- **现状**：创建 Agent 的 runtime 下拉有 `codex` / `deepseek`，但仅实现 claude
- **方案**：要么实现多 runtime，要么从 UI 移除避免误导

### 🟢 P3 — 体验锦上添花

#### 15. Web Bundle Code-Split
- **现状**：~690KB 单 chunk，构建有 >500KB 警告
- **方案**：按路由 `React.lazy()` + `import()` 拆分

#### 16. Agent 头像
- **现状**：profile show/update 无头像字段
- **切入点**：复用现有 attachment 存储体系

#### 17. 移动端适配
- **现状**：桌面优先，移动端布局可优化

### 🟡 P4 — Slock 进阶差异化（需较多基建）

#### 18. 自主 Agent 生命周期
- **现状**：仅被动响应 @ / DM / 提醒
- **目标**：常驻心跳巡检、自驱认领任务、长任务续跑
- **建议**：最小版起步（开关 + 限频）

#### 19. 第三方集成深度
- **现状**：`/api/integrations` 仅 stub
- **路径**：出站 Webhook → per-agent 凭证注入 → OAuth 代理

#### 20. 权限 / 审计
- **现状**：角色权限较粗（owner/admin/member），无操作审计日志
- **目标**：细粒度权限模型 + `audit_log` 表记录所有改写操作

#### 21. 容器化 / 部署就绪
- **现状**：`docker-compose.yml` 挂载的 `schema.sql` 已改名失效
- **修复**：更新 compose 中的挂载路径
- **增强**：环境变量必填校验、生产 cookie 加 `Secure` 标志
