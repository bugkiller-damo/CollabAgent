## 三、严重问题（Critical）

### CRIT-1: 并发探测目标数前后矛盾

**位置**: §2.1 量化指标表（第 115 行） vs §2.1 总体目标、§3.2.3、§5.3、§6.2.2  
**类型**: 逻辑一致性

**描述**: 核心量化指标表中"单节点并发探测目标数"为 **≥ 10**，但文档其余五处均为 **≥ 100**：

| 位置 | 内容 |
|------|------|
| §2.1 总体目标 | "单节点支持不少于 **100** 个目标的并发探测" |
| §2.1 量化指标表 | "单节点并发探测目标数 ≥ **10**" ← **矛盾** |
| §2.1 测量口径说明 | "单节点并发探测目标数 ≥ **100**" |
| §3.2.3 引擎调度 | "单节点支持不少于 **100** 个目标并发探测" |
| §5.3 性能需求 | "单子公司节点并发探测目标数 ≥ **100**" |
| §6.2.2 验收标准 | "单子公司节点并发探测目标数 ≥ 100" |

**影响**: 10 倍差距导致容量设计基准混乱。按 10 设计则无法满足其余章节的 100 要求。

**建议修复**: 将 §2.1 量化指标表中"≥ 10"修正为"≥ 100"。

---

### CRIT-2: 病例库 API 完全缺失

**位置**: §4（接口需求）  
**类型**: 需求完整性

**描述**: §3.4.5 明确病例上报使用 "RESTful API 调用"，§3.1.2.6 定义了 8 步病例分发流程（含拉取、状态更新），§3.2.4 定义了病例搜索、上报、接收功能。但 **§4 接口需求章节没有定义任何病例库 API 端点**：

| 缺失端点 | 对应功能 |
|----------|----------|
| `POST /api/v1/cases` | 病例上报 |
| `GET /api/v1/cases` | 病例检索（含全文搜索、多维过滤） |
| `GET /api/v1/cases/{case_id}` | 病例详情获取 |
| `PUT /api/v1/cases/{case_id}/status` | 病例修复状态更新 |
| `POST /api/v1/cases/{case_id}/feedback` | 退订/误报反馈 |
| `GET /api/v1/cases/notifications` | 病例分发通知拉取 |

病例库是系统核心知识资产，其 API 缺失是接口规范中最大的空白。

**影响**: 平台开发组和渗透开发组缺乏病例数据交换的接口规范，无法实现 §3.1.2 和 §3.2.4 定义的功能。

**建议修复**: 新增 §4.6 病例库 API，参考 §4.1 的详细程度定义所有端点。

---

### CRIT-3: 协调智能体功能规格缺失

**位置**: §3.3  
**类型**: 需求完整性

**描述**: 架构图中多处出现"协调智能体"（MultiAgent），§4.1.8 日志过滤参数中包含 `coordinator`，§5.1.2 要求"关键决策须经协调智能体二次确认"。但 §3.3 中侦察、规划、执行、提权、横向移动智能体各有独立子节（3.3.1-3.3.4），**唯独协调智能体没有功能规格子节**。

协调智能体在架构上承担关键角色：
- 是子公司智能体与渗透引擎的唯一 API 接触点（架构图显示）
- 负责任务分发、智能体调度、状态协调
- 承担 Exploit 执行的二次确认职责

**影响**: 渗透开发组缺少协调智能体的功能定义，可能实现为一个简单的消息路由而非具备协调逻辑的智能体。

**建议修复**: 新增 §3.3.0 协调智能体功能规格，明确定义其任务分发、状态协调、二次确认、异常降级逻辑。

### CRIT-4: 渗透测试员划入"管理员"三权分立域，违背职权分离原则

**位置**: §5.4.2（第 1892 行）  
**类型**: 安全设计

**描述**: §5.4.2 三权角色与 RBAC 映射表将"渗透测试员"映射到"管理员"域。渗透测试员拥有执行渗透任务的能力，若同时属于管理员域（含系统管理员权限），则一个被攻陷的渗透测试员账号可导致：篡改系统配置、关闭审计日志、修改病例库数据。

这与等级保护 2.0 的"最小权限"和"职权分离"原则冲突。

**影响**: 三权分立的安全价值被严重削弱——操作权限（渗透执行）与管理权限（系统配置）不应合并。

**建议修复**: 将三权角色从三个扩展为四个域：
- **管理员**：系统配置、用户管理、策略管理（不可执行渗透）
- **操作员**：仅执行渗透任务及查看自己的执行结果（新增，从管理员域分离）
- **审计员**：只读审计日志（不变）
- **只读用户**：查看报告、看板、病例（不变）

### CRIT-5: 缺乏系统自身的 Web 应用安全要求

**位置**: §5.1（安全性）  
**类型**: 安全需求缺失

**描述**: §5.1 覆盖了渗透操作的命令注入防护、沙箱逃逸防护、反向控制防护和 LLM 安全，但**完全没有覆盖管理平台自身**的安全要求：

| 缺失项 | 说明 |
|--------|------|
| **SQL 注入防护** | 系统使用 PostgreSQL，API 端点涉及病例检索、资产管理、任务查询等数据操作，须要求参数化查询 |
| **CSRF 防护** | 管理控制台的状态变更操作（策略下发、任务创建、病例审批）须防护跨站请求伪造 |
| **XSS 防护** | 安全监管看板和人机共融界面展示智能体对话内容（含目标系统返回数据），须输出编码 |
| **CSP 头** | 管理控制台页面须实施 Content Security Policy |
| **文件上传安全** | 病例附件（最大 10MB）和 PoC 文件上传须限制类型、扫描恶意软件、安全处理文件名 |

**影响**: 管理平台自身若被攻陷，攻击者可获取全集团漏洞数据、PoC 和渗透工具——比普通系统沦陷更危险。

**建议修复**: 在 §5.1 新增"管理平台自身安全"子节，覆盖 OWASP Top 10 防护要求。

---

### CRIT-6: 缺乏密钥与凭证管理方案

**位置**: §5.1.3、§4.1.12、§4.3  
**类型**: 安全需求缺失

**描述**: 文档多处使用密钥和凭证：OAuth client_secret、数据库密码、LLM API Key、Webhook 签名密钥、KMS 密钥、TLS 证书。但**整个文档没有定义密钥如何安全存储、分发、轮转和销毁**。

§4.1.12 要求 Token "仅存储于内存（不落盘）"，但 client_secret 本身必然落盘于配置文件，未说明如何保护。

**影响**: 泄漏一个 client_secret 即可伪造渗透引擎 API 调用；泄漏 LLM API Key 可窃取/污染所有智能体推理。

**建议修复**: 在 §5.1 新增密钥管理要求：
- 所有密钥通过密钥管理服务（HashiCorp Vault / KMS）管理
- 禁止密钥硬编码在配置文件或代码中
- 建立密钥轮换策略和紧急吊销机制
- 数据库密码加密存储，运行时从 KMS 解密

## 四、高级问题（High）

### HIGH-1: 任务控制 API 操作枚举不完整

**位置**: §4.1.4 vs §4.1.1 vs §3.2.3  
**类型**: 逻辑一致性

**描述**: §4.1.1 描述任务控制接口为"暂停/恢复/停止/**强制终止**"（4 种操作），§3.2.3 也提到"强制终止"。但 §4.1.4 action 可选值仅 3 种：`pause`、`resume`、`stop`。缺少 `force_terminate`。

此外，§4.1.6 任务列表过滤 status 选项中有 `terminated`，但 §4.1.4 的 action 值用的是 `stop`——命名不一致。

**建议修复**:
- 补充 `terminate`（强制终止）操作
- 明确 `stop`（优雅停止，保存检查点）与 `terminate`（立即终止，不保存）的区别
- 统一命名：action 值与 status 枚举值对应

**位置**: §4.1.6（第 1213-1217 行）

### HIGH-3: 协作平台通信接口定义严重不完备

**位置**: §4.2  
**类型**: 需求完整性

**描述**: 对比 §4.1 渗透引擎 API（11 个端点、完整请求/响应 JSON、参数表、错误码表），§4.2 协作平台仅给出了高层概述。缺失：

| 缺失项 | 影响 |
|--------|------|
| WebSocket 端点路径 | 无连接端点定义 |
| HTTP REST 消息拉取端点 | 虽提及但无具体路径/参数 |
| 通道管理 CRUD API | 创建/删除/加入/退出通道无接口定义 |
| WebSocket 鉴权方式 | Token 传递方式未定义 |
| 心跳/重连策略 | 断线行为未定义 |
| 消息确认（ACK）格式 | 格式和超时标准未定义 |

Sprint 4（7 月下旬）即需交付协作平台初版，当前接口规范不足以支撑开发。

**建议修复**: 参考 §4.1 详细度，补充 WebSocket 端点、HTTP REST 端点、通道管理 API、鉴权和重连策略。

### HIGH-4: 规划智能体 LLM 代理模式存在瓶颈风险

**位置**: §3.3（第 701-704 行）  
**类型**: 架构设计

**描述**: 规划智能体的 LLM 调用须通过子公司智能体代理转发：规划智能体 → 子公司智能体 → LLM → 子公司智能体 → 规划智能体。每次推理增加 2 跳网络延迟。当 10 个并发任务同时需要 LLM 推理时（每任务 × 3 次推理 = 30 次/轮），子公司智能体成为瓶颈。

此外，§5.3 定义 LLM 推理 P95 < 8s，但未说明是否包含代理转发延迟。

**建议修复**:
1. 明确 LLM 延迟测量口径（是否含代理转发）
2. 定义子公司智能体的 LLM 代理并发上限
3. 考虑"规划凭证"机制：子公司智能体预批一组规划决策供渗透引擎本地执行，仅在异常情况下回调

---

### HIGH-5: 双平面通信冲突检测机制不足

**位置**: §2.2 架构约束 + §2.3.2 异常处理表  
**类型**: 技术细节不足

**描述**: 双平面通信设计已明确（协作平台主通道 + API 兜底），冲突默认 API 优先。但以下关键机制缺失：

| 缺失细节 | 说明 |
|----------|------|
| 数据版本机制 | "自动比对两者数据版本"——版本号生成规则未定义（Lamport 时钟？时间戳？） |
| 冲突检测粒度 | 按消息 ID 逐条比对还是按业务对象比对？ |
| 冲突解决窗口 | 协作平台恢复后多久内进行比对？ |
| 审计完整性 | API 优先覆盖操作的审计日志是否完整？ |

**建议修复**: 补充消息版本号生成规则（建议发送方单调递增序列号 + 发送方 ID）、检测窗口（建议 1 小时）和审计日志要求。

**位置**: 全文（§2.2 仅有逻辑架构图）  
**类型**: 需求完整性

### HIGH-7: 时间线可行性风险

**位置**: §6.1  
**类型**: 项目计划

**描述**: 该系统的完整范围——分布式多智能体平台、AI 驱动渗透引擎、病例库知识管理、实时协作平台——通常需 20-30 人 × 12+ 个月。当前计划 8-11 人 × 4 个月（6-9 月），关键风险：

- Sprint 1-2（6 月）架构设计 + 初赛材料并行，人员精力分散
- Sprint 3-4（7 月）需同时交付链式操作闭环 + 协作平台 v1
- 三组并行开发未留出集成联调缓冲
- §6.1.3 将"系统安全加固"等 P0 项推迟至 10 月（比赛结束后），但 §6.2.3 要求比赛交付物通过安全测试——存在矛盾

**建议修复**: 明确定义 MVP 范围缩减标准；补充集成测试阶段（Sprint 5-6 之间）；评估 §6.1.3 P0 安全项是否需要前移至比赛阶段。

---

### HIGH-8: 缺乏服务间 mTLS 强制要求

**位置**: §4.3、§5.1.3  
**类型**: 安全需求

**描述**: §5.1.3 数据安全表中仅"智能体通信"标记了 mTLS，但集团平台↔子公司平台 API 直连、子公司平台↔渗透引擎 API、管理平台↔协作平台 WebSocket 均未要求 mTLS。在内部网络横向移动攻击场景下，缺乏 mTLS 的组件间通信可被中间人攻击。

**建议修复**: 所有内部服务间调用强制 mTLS；建立内部 CA 和证书生命周期管理。

---

### HIGH-9: 缺乏软件组成/依赖漏洞管理

**位置**: §5.1  
**类型**: 安全需求缺失

**描述**: 系统依赖 PostgreSQL 15+、Redis 7+、Kafka/Redis Streams、Elasticsearch、nginx、Docker 等组件，以及各语言生态的第三方库。文档未要求对这些依赖进行 CVE 跟踪、SBOM 管理或定期扫描。渗透测试系统自身若因 Log4j 类依赖漏洞被攻陷，后果比普通系统更严重。

**建议修复**: 在 §5.1 增加 SBOM 管理要求；CI/CD 集成依赖扫描（trivy/grype）；建立 CVE 响应 SLA（Critical 级别 48h 修复）。

---

### HIGH-10: Web 应用漏洞发现率基准假设有缺陷

**位置**: §2.1 测量口径说明  
**类型**: 可测试性

**描述**: 发现率公式为"自动化发现的真实漏洞数 ÷ 人工确认的漏洞总数"。这假设人工渗透具有 100% 召回率——即能找到所有实际存在的漏洞，这不现实。更可靠的方法应使用已知 Ground Truth 的基准测试靶场（如 Xbow Benchmark）作为分母。

**建议修复**: 修改基准为已知漏洞数量的标准测试靶场，而非依赖人工渗透结果。

---

### HIGH-11: LLM 推理延迟指标缺少硬件前提

**位置**: §5.3  
**类型**: 可测试性

**描述**: §5.3 定义"LLM 单次推理 P95 延迟 < 8 秒"。对于 Qwen3.5-397B-A17B（397B 参数），8 秒 P95 推理延迟需要特定硬件配置（多张 H100/A100 GPU + tensor parallelism）。文档未说明硬件假设，该指标无法评估。

**建议修复**: 补充 LLM 推理的目标硬件配置，或定义"等效于 X 张 Y GPU 配置下"的延迟目标。

---

### HIGH-12: 缺乏容器运行时安全加固的完整要求

**位置**: §5.1.1、附录 A  
**类型**: 安全需求

**描述**: §5.1.1 要求 Docker 沙箱加 Seccomp/AppArmor，但未覆盖：只读根文件系统、Linux capabilities 最小化、容器间网络策略、镜像签名验证。渗透容器持有恶意负载（PoC、Exploit），容器逃逸风险极高。

**建议修复**: 补充容器安全加固矩阵（只读 rootfs、cap-drop-all、NetworkPolicy deny-all、镜像签名、考虑 gVisor/Kata）。

---

### HIGH-13: LLM 提示注入防护措施过于模糊

**位置**: §5.1.1、§6.2.3  
**类型**: 安全需求

**描述**: §5.1.1 对 LLM 提示注入防护描述为"对非结构化数据进行清洗，识别并屏蔽潜在的指令引导字符；增加确定性数据过滤层"，缺乏可测量、可验证的实现标准。§6.2.3 要求"验证有效"但无通过标准。

**建议修复**: 定义威胁模型（直接/间接注入、上下文/角色注入）；建立 ≥ 50 种已知注入模式的测试用例集；多层防御（输入清洗 + LLM 输出验证 + 操作执行前确认）。

## 五、中级问题（Medium）

### MED-1: 链式操作深度定义与状态机不一致

**位置**: §2.1 边界约束 vs §3.3.5 状态机  
**类型**: 逻辑一致性

§2.1 边界约束定义链式操作最大深度为"5 层（侦察→利用→提权→横移→**持久化**）"，但 §3.3.5 状态机只展示"侦察 → 规划 → 利用 → 提权 → 横向移动 → 结果汇总"，不含持久化。持久化在 §3.3.4.2 被列为横向移动智能体的功能之一，但不是一个独立的链式操作阶段。

**建议修复**: 明确持久化是横向移动的子功能还是独立阶段，统一边界约束和状态机的描述。

---

### MED-2: task_type 注释与示例值不一致

**位置**: §4.1.2  
**类型**: 逻辑一致性

代码注释 `// 目前默认传full` 说默认值是 "full"，但示例 JSON 值是 `"full_penetration"`。

**建议修复**: 统一注释和示例值，并定义完整的 task_type 枚举。

---

### MED-3: 任务下发 timeout 与 duration 参数交互不明确

**位置**: §4.1.2  
**类型**: 歧义

`timeout: 3600`（隐含秒）和 `duration: 120`（分钟）同时存在，两者都约束执行时间但语义重叠。duration 是否覆盖 timeout？还是 timeout 为硬截止、duration 为计划时长？

**建议修复**: 明确两个参数的语义关系，建议 timeout 为硬截止（保护性），duration 为计划攻击窗口。

---

### MED-4: 任务完成后结果获取缺少分页支持

**位置**: §4.1.7  
**类型**: API 设计

单次渗透任务可能发现数百个漏洞，`GET /api/v1/tasks/{task_id}/results` 一次性返回全部结果无分页支持，可能导致响应超时或内存溢出。

**建议修复**: 为 vulnerabilities 数组增加分页参数。

---

### MED-5: 攻击图无独立增量获取 API

**位置**: §4.1  
**类型**: API 设计

攻击图（attack_graph）仅在任务完成后的 results 端点返回。对于持续数小时的任务，安全分析人员无法实时查看攻击路径演进。§3.2.3 要求"实时展示渗透攻击图"但无对应 API。

**建议修复**: 增加 `GET /api/v1/tasks/{task_id}/attack-graph` 端点，支持增量获取。

---

### MED-6: RAG 知识库架构未定义

**位置**: §3.3.2  
**类型**: 架构设计

RAG 知识库（粗粒度攻击知识、过程级攻击知识、执行历史）被多次引用，但未定义：集中式还是分布式？更新机制？嵌入模型？向量数据库选型？离线子公司如何访问？

**建议修复**: 定义知识库管理子系统架构，含同步机制和本地缓存策略。

---

### MED-7: 缺乏数据库备份/恢复 RTO/RPO

**位置**: §5.2  
**类型**: 非功能需求

§5.2 提到"数据库每日全量备份 + 实时增量备份"，但未定义备份恢复的 RTO 和 RPO，也未要求定期恢复演练。

**建议修复**: 补充备份恢复 RTO/RPO 目标和定期演练要求。

---

### MED-8: 多租户数据隔离强度依赖应用层实现

**位置**: §3.2.5  
**类型**: 安全需求

任务和资产数据隔离使用"数据库行级隔离（SubsidiaryID 字段）"，完全依赖应用代码正确传递 SubsidiaryID。一次编程错误即可导致跨子公司数据泄露。

**建议修复**: 考虑数据库层面增强隔离（PostgreSQL Row-Level Security 或 Schema 级隔离）；补充隔离有效性的自动化测试要求。

---

### MED-9: Webhook 回调 event_id 去重未防护

**位置**: §4.1.11  
**类型**: 安全需求

Webhook 签名验证用时间戳防重放（300s 窗口），但 300s 内相同 event_id 的重放攻击未防护。

**建议修复**: 子公司侧维护已处理 event_id 的去重缓存（TTL = 300s + 时钟偏差容忍）。

---

### MED-10: 缺乏离线自治模式下的脑裂检测

**位置**: §3.2.1  
**类型**: 架构设计

子公司离线时自主运行，但与集团恢复连接后，本地决策可能与集团策略冲突（如集团在离线期间更新了策略）。无机制检测和处理这种"脑裂"状态。

**建议修复**: 定义重连时的策略版本比对机制；子公司重连后优先同步策略更新再处理积压数据。

---

### MED-11: Token 刷新缺少惊群效应防护

**位置**: §4.1.12  
**类型**: 技术细节

Token 有效期 1 小时，过期前 5 分钟刷新。多渗透引擎实例（如 60 个）同时触发刷新将产生惊群效应。

**建议修复**: 刷新时间增加随机抖动（jitter），如过期前 5 分钟 ± 随机 0-60 秒。

---

### MED-12: 第三方 API 数据投毒检测规则不明确

**位置**: §5.1.1  
**类型**: 安全需求

§5.1.1 定义第三方 API（Shodan/Fofa/Qualys）异常数据自动屏蔽，但"异常数据"的检测规则未定义。

**建议修复**: 定义具体校验规则（扫描结果字段完整性、CVSS 合理性范围、时间戳新鲜度、响应结构 Schema 校验）。

---

### MED-13: 缺乏安全开发（DevSecOps）集成要求

**位置**: §6.1.2 Sprint 计划  
**类型**: 过程

Sprint 计划中未包含任何安全开发活动（威胁建模、SAST/DAST 扫描、安全设计评审）。§6.1.3 将安全加固列为 P0 但仅在 10 月生产化阶段开始——意味着比赛阶段交付物无系统安全保证。

**建议修复**: 在每个 Sprint 中集成安全活动（威胁建模在 Sprint 1-2、SAST 在 Sprint 3+、DAST 在 Sprint 5+）。

---

### MED-14: 缺少渗透测试报告生成功能

**位置**: §3  
**类型**: 功能缺失

结果 API 返回结构化 JSON，但无人类可读的渗透测试报告生成需求（PDF/HTML）。§3.2.6 仅提到病例导出，未涉及任务报告。

**建议修复**: 新增渗透测试报告生成功能需求。

## 九、总结

### 9.1 整体评价

v1.3 是一份**持续改进中的高质量需求规格说明书**。v1.2 审核中发现的 10 个问题已全部修复，体现了严谨的文档迭代态度。当前版本（74.6 分）距优质级门槛（75 分）仅差 0.4 分。

**核心优势**：
- 15+ 异常处理场景含恢复策略，业界少见
- 渗透引擎 API 设计详尽，可直接开发
- 数据生命周期管理、多租户隔离、审计追踪要求清晰
- 安全纵深防御体系统完善（渗透操作安全层面）

**关键差距**：
