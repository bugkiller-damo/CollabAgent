## 1. 体系概述

Slock 是 AI-native 团队协作平台：人类与 AI 智能体（agent）在同一频道体系里对话、派任务、协作。每个 agent 的本体是用户本机 daemon 进程拉起的一个 **Claude Code PTY 子进程**——agent 的思考、工具调用、代码能力全部来自 Claude Code 本体，平台负责消息路由、身份凭证、生命周期和可观测性。

```
┌──────────┐   REST / WS    ┌──────────┐   WS(/ws)    ┌──────────┐   PTY    ┌─────────────┐
│ Web 浏览器│ ◄────────────► │  Server  │ ◄──────────► │  Daemon  │ ◄──────► │ Claude Code │ × N agents
│ (React)  │                │ (Fastify)│              │ (node-pty)│         │  子进程      │
└──────────┘                └────┬─────┘              └────┬─────┘          └──────┬──────┘
                                 │ PostgreSQL               │ .slock/ 本地态         │ MCP stdio
                            业务数据/凭证                run 记录/工作区/日志      slock-mcp-server
                                                                          → /internal/agent/*
```

部署形态：server 单实例（PostgreSQL）；daemon 跑在 agent 所有者的机器上，一个账号一条 daemon 连接（machine token 认证），可托管该账号名下多个 agent；agent 通过 MCP 工具（或 slock CLI）回调 server 的 `/internal/agent/*` 完成发言与协作。

**当前仅支持 Windows**（跨平台暂缓）；agent 运行时仅支持 Claude Code。

## 3. Agent 状态机

五个状态（`agent-runtime-state.ts`）：

| 状态 | 语义 |
|------|------|
| `uninit` | 未初始化（注册后、首次启动前） |
| `idle` | 空闲（无 live run，或 run 存活但回合已结束） |
| `starting` | 启动中（PTY spawn 流程进行中） |
| `working` | 工作中（有待处理消息 / Claude 正在输出） |
| `stopped` | 已停止（显式注销，dispatch 直接跳过） |

合法迁移：

| 当前 → 允许 |
|--------------|
| uninit → idle, stopped |
| idle → starting, working, stopped |
| starting → working, idle, stopped |
| working → idle, stopped |
| stopped → idle |

语义要点：

- 非法迁移：`assertTransition` 抛错，`transitionState` 捕获后**静默忽略**（不崩溃，只 warn）。
- 同态迁移是 no-op（退出清理链重复回 idle 不报警）。
- `idle → working` 合法：PTY 复用分支不经过 starting。
- **崩溃退出回 idle 而非 stopped**：stopped 是显式注销语义，会被 doDispatch 拦截；回 idle 使下一条消息能重新 spawn。
- 启动超时：starting 挂 15s startupTimer，超时回 idle。
- 每次迁移记录 `lastTransitionAt`，供 STUCK 检测计算 working 时长。

## 4. 消息协作流

### 4.1 @mention 全链路

```
用户              Server                    Daemon                   Claude Code PTY
 │ POST /messages/send│                        │                          │
 │───────────────────►│                        │                          │
 │                    │ ① mentionAgents 预过滤  │                          │
 │                    │   (事务内, §4.2)        │                          │
 │                    │ ② broadcast            │                          │
 │ ◄── agent:deliver ─┤─── agent:deliver ─────►│                          │
 │                    │                        │ ③ choke points (§4.3)    │
 │                    │                        │ ④ dispatchToAgent        │
 │                    │                        │   + REMINDER_TAIL        │
 │                    │                        │ ⑤ spawn 或复用 PTY ─────►│
 │                    │                        │   bootstrap+消息合并写入  │ ⑥ 读 CLAUDE.md
 │                    │                        │                          │   思考/工具调用
 │                    │ ◄── POST /internal/agent/:id/send (MCP send_message)│
 │ ◄── agent:deliver ─┤                        │                          │
 │                    │                        │ ⑦ 回合结束检测 → idle     │
```

① **mentionAgents 预过滤**（server，事务内）：公开频道候选 = 本组织全部 agent ∪ 发送者名下 agent，用 `contentMentions` 子串匹配（支持中文名，名字后不能紧跟字母/数字/下划线）；命中者自动 INSERT 进 channel_members；私有频道候选仅为已入圈 agent，不自动入圈。结果放入广播消息的 `mentionAgents` 字段。DM 不走 mentionAgents，改附 `dmAgentRecipients`。

② **broadcast**：公开频道全发；私有/DM 仅发人类成员的浏览器（daemon 全发，daemon 侧过滤）。

③ **daemon choke points**（`daemon-core.ts`，任一命中即丢弃）：
- 内容以 `🤖 ` 开头（系统前缀防环）；
- `forceDeliverTo` 存在 → 绕开防自环直接路由（派发通知专用）；
- `senderType === "agent"` → 丢弃（防 agent 互 @ 死循环）；
- DM → 对 dmAgentRecipients 逐个 runAgentDm（无需 @）；
- 频道：`mentionAgents` 字段存在（含空数组）→ 只路由列表中第一个本 daemon 注册的 agent；**空数组 = 有人被 @ 但无人有权回应，不 spawn**（区别于字段缺失 = 旧 server，本地文本解析兜底）；
- `senderId === 本 daemon agentId` → 丢弃；
- `hasAgent()` 只认本 daemon 注册的 agent（loadExistingAgents 用 `?mine=1` 只拉本账号 agent，避免 spawn 时换凭证 403）。

④ **dispatchToAgent**：统一追加 REMINDER_TAIL（见 §4.4）；同 agent 已有 in-flight dispatch 时，新消息**挂到该 agent 的 promise 链尾部串行排队**（2026-07-29 起，此前是 await 后丢弃）——前一条失败不阻塞后续（`.catch` 隔离），链尾清理防止 Map 泄漏。排队时经 `onDeliveryQueued` 回调向 server 发 `agent:delivery-queued` 事件，server 中继给属主浏览器，前端 toast"消息已缓冲，将在其空闲后自动投递"——用户连续发消息不再静默丢失。两条路径：
- **新 spawn**：idle→starting（15s 超时）→ 建工作区 → mint scoped token（失败整次启动失败，不退回共享 apiKey）→ 拉 dispatchContext → 写系统提示 → spawnPtyForAgent → starting→working。
- **PTY 复用**：idle→working，直接 postStartWriter 写入。

⑤ **spawnPtyForAgent**：写 `.mcp.json` + `enableAllProjectMcpServers` + `effort`（默认 medium，`SLOCK_AGENT_EFFORT` 可调——Claude Code 2.1.x 会话默认 high，thinking token 照付；⚠️ settings 键名未经官方文档证实，不识别则静默忽略）；参数 `--dangerously-skip-permissions --permission-mode=bypassPermissions --disallowedTools=Task` + 可选 `--model`（校验 `^[a-z0-9._-]+$`）+ `--resume <sessionId>`（**默认开启**，`=0` 关闭）；等 terms 对话框 → CLAUDE.md 落盘 → bootstrap（系统说明 + 身份 + 恢复摘要 + "去读 CLAUDE.md" 指针）与**触发消息合并成一次写入**；5s 后捕获 sessionId。

⑥ Claude Code 自主工作，用 MCP `send_message`（或 slock CLI）把回复 POST 回 server → 落库 + 广播。

⑦ **回合结束检测**（输出订阅回调）：working 且有 pending → 当前帧出现 `esc to interrupt` → 标记 busyObserved；忙碌消失 + 有提示符 `❯/›` + **曾观察到忙碌** → pending 清除 + working→idle + idleReclaimer.touch。三条件缺一不可；看的是 xterm 渲染后的当前帧而非原始字节流。另有**静默兜底**：20s（SLOCK_QUIESCE_MS）无任何输出且有提示符 → 直接判回合结束（兜住"wait quietly"这类从没出现忙碌帧的安静回合）。

### 4.2 mentionAgents 的三种取值语义

| 取值 | 语义 | daemon 行为 |
|------|------|-------------|
| 非空数组 | 这些 agent 有权回应 | 路由第一个本机注册的 |
| 空数组 | 有人被 @ 但无人有权回应 | 不 spawn（零 PTY 成本拦截） |
| 字段缺失 | 旧版 server | 本地文本解析兜底 |

### 4.3 经理/worker 派发流

人类在频道设置某 agent 为经理（`channel_members.is_manager`，每频道一名）。经理 agent 调 MCP `dispatch_task` → server 校验 isChannelManager + worker 是频道成员 → 插 `dispatches` 行 + 一条 sender_type=agent 的消息，broadcast 带 `forceDeliverTo` → daemon 绕过防自环直接路由给 worker。worker 完成后 `report_task` → status=reported + 同链路通知经理。经理可 `cancel_dispatch`（仅 open 状态）。

**dispatch↔任务看板同步**（2026-07-29，迁移 009 `dispatches.task_message_id`）：派发时那条 📋 通知消息原子取号补 `task_number` 直接成为看板卡片（`in_progress` + `task_assignee`=worker——复用原消息行，非新建副本）；`report_task` → 卡片转 `in_review`（等经理审查）；`cancel_dispatch` → 卡片转 `closed`。派发体系与看板从此单一事实源，演示"派发→看板自动流转"全连贯。相关：人类也可在任意频道消息上点"📋 转任务"（`POST /api/tasks/from-message`，同样是给既有消息行补 task_number；重复转换 409 / 已删除 400 / 无权限 403）。

### 4.4 REMINDER_TAIL

dispatchToAgent 在每条投递消息尾部追加：

```
<slock-reminder>你是 @X（CollabAgent 平台的 AI Agent）。对外回复只能用 send_message
工具（或 slock CLI），直接打字不会被发送；回合开始先读工作区里的 MEMORY.md。</slock-reminder>
```

目的：对抗 Claude Code `/compact` 把系统提示压缩掉之后 agent"忘记"发言协议。CLAUDE.md 抗压缩管"静态规则"，REMINDER_TAIL 管"每条消息都提醒一次"。

### 5.2 token 生命周期

```
mint (spawn 前)                使用期间                     回收
POST /internal/agent/    ──►  注入 MCP env / CLI env   ──►  退出清理链：服务端 revoke (best-effort)
  :id/credentials            (sk_agent_, 24h TTL)           + 本地 revokeIfMatches
  upsert 覆盖 = 撤旧
```

- daemon 的账号级 machine token **永不进子进程 env**——子进程只拿 scoped token。
- mint/revoke 端点拒绝 scoped token 调用（scope=agent-run → 403），防泄露后自我续期。
- 本地 `agent-tokens.ts` 用 `timingSafeEqual` 校验；`revokeIfMatches` 保证旧进程退出回调不会误删新 run 的 token（竞态双保险之一，另一层是服务端 upsert 覆盖）。

### 5.3 退出清理链（顺序敏感）

`agent-runtime-exit.ts`：exitCoordinator.onExit → exitHandler（revokeIfMatches + runStore 落盘）→ 服务端 revoke scoped token → 取消输出订阅 → idleReclaimer.untrack → turnTracker 重置 → runIdByAgent 条件清理（仅当仍指向该 run，防竞态）+ 状态机回 idle → 终端日志落盘（须在 removeRun 前取 historyText）→ agentManager.removeRun。

退出码：0 → "exited"；其余 → "error"；**129 = 128+SIGTERM = idle 回收**，restart-summary 显示"reclaimed（回收）"而非错误。

### 5.4 崩溃恢复与单实例守卫

- **planned-restart 标记**：supervisor watch 重启与 DaemonCore.stop() 都先写 `.slock/planned-restart`；daemon 构造时检测到标记则跳过崩溃恢复处理并删除标记——区分"计划内停止"与"崩溃"。
- **采集顺序不变量**：候选列表（runStore.listActiveAgents，查 status 为 starting/running 的记录）必须在 `markUnfinishedRunsStale()` 之前采集，否则状态被改写后永远查空。
- **崩溃恢复 = lazy，不再 eager autostart**（2026-07-29 起）：旧实现给每个候选 agent 注入"系统重启，安静等待"恢复消息并走完整 dispatchToAgent——但那是一整个 agent 回合（实测 55k 输出、1m23s）且 99% 的结论是"没有真实消息，静默等待"，纯烧 token。新行为只记日志；agent 保持 lazy 注册，下一条真实消息到来时再 spawn，上下文由 session resume（默认开）或 restart-summary 注入保住。
- **单实例守卫**（2026-07-29）：`index.ts` 启动时读 `.slock/daemon.pid`，旧 PID 存活则整树杀掉再起；supervisor 重启/关闭用 `taskkill /T /F`（Windows）整树杀子进程。背景：`shell:true` spawn 的 plain `kill()` 只杀 cmd 包装层，node 孙子进程成孤儿——新旧两个 daemon 并存时日志全双份、每个 agent 被重复 spawn（**双倍 token**）、且新实例 mint scoped token 会 upsert 撤旧，旧实例 PTY 里的 MCP 调用全部 401。单实例后该时序不可能再出现。

## 6. 终端观察体系

```
AgentTerminalPanel (web)                server ws handler            daemon
 ┌ 实时画面(pre) ◄── terminal:frame ◄── 仅推观众集合 ◄── 400ms 推帧(去重)
 ├ 历史日志(pre) ◄── terminal:history ◄── 中继 ◄── scrollback/磁盘日志
 └ 拖宽/字号 ── terminal:resize ──────► 中继 ──────► setPreferredTermSize
                                                     + resizeRun(pty.resize)
                                                     → Claude Code 收 SIGWINCH 重排
```

- **terminal-state**：`@xterm/headless` Terminal，scrollback 1000。`getScreenText()` 从 `buf.baseY` 起读 `term.rows` 行——scrollback>0 时 getLine(0) 是最老历史行，漏掉 baseY 会导致面板只见启动画面（实测 bug，已修并有回归测试）。
- **推帧**：`terminal:watch` → 先补历史（运行中 run 的 historyText，否则读磁盘日志尾部 60KB）→ 立即一帧 → 400ms setInterval，key = status+"|"+screen 去重。unwatch 清定时器。server 侧按观众引用计数中继（首个观众才 watch，最后一个离开才 unwatch）。
- **磁盘日志**：每次 run 退出时把终端画面（渲染后纯文本）追加到 `.slock/terminal-logs/<safe>.log`，带 `run <id8> · 结束于 <时间> · exit=<code>` 分隔头；单文件 >512KB 截断保留尾部 256KB。agent 被回收后仍可回看。
- **resize 协商**：面板按可视区算 cols/rows（字宽=字号×0.6，行高=字号×1.5，防抖 300ms）→ daemon clamp（20-400 列 × 5-100 行）→ `pty.resize`（SIGWINCH）+ 终端镜像同步 resize；偏好尺寸被记住，下次 spawn 直接按偏好尺寸启动。

## 8. 安全与权限模型

| 层 | 机制 |
|----|------|
| agent 归属 | `agents.user_id` = 所有者；所有 `/internal/agent/:agentId/*` 前置 `requireOwnAgent`；daemon 只注册本账号 agent（`?mine=1`）；`agent:start` 只推所有者 daemon |
| 凭证隔离 | scoped token（24h，agent 级）与 machine token（账号级）分离；daemon apiKey 不进子进程；mint 需账号级 token |
| 发言权限 | mentionAgents 预过滤在 server 侧完成——无权 agent 连 PTY 都不会起（零资源浪费）；私有频道不自动入圈 |
| 频道可见性 | agent 自主 join 仅限公开频道；私有需频道管理员 invite；DM recipients 由 server 计算 |
| 防环 | senderType=agent 的消息不触发 agent；`🤖 ` 前缀丢弃；forceDeliverTo 仅派发链路使用 |
| 经理权限 | dispatch 仅 is_manager agent 可调（服务端校验）；report/cancel 各自校验 from/to 归属 + open 状态 |
| token 竞态 | 本地 revokeIfMatches + 服务端 upsert 覆盖 双保险；runIdByAgent 条件清理 |

## 9. 设计不变量

以下不变量是多处 bug 修复沉淀的结论，改动相关代码时必须保持：

1. **bootstrap 与首条用户消息必须合并成一次写入**——两次独立写入会产生两个就绪轮询定时器的竞态。
2. **回合结束 = pending + 曾观察到忙碌 + 当前空闲有提示符**，三者缺一不可；判据是 xterm 渲染后的当前帧，不是原始字节流。
3. **pending/busyObserved 是布尔语义**——重叠消息只产生一次回合结束信号，计数语义会永远清不干净。
4. **token 竞态双保险**：本地 revokeIfMatches（旧进程退出不误删新 token）+ 服务端 upsert（重签即撤旧）。
5. **崩溃回 idle 而非 stopped**——stopped 是显式注销语义，会被 dispatch 拦截。
6. **mentionAgents 空数组语义** = "有人被 @ 但无人有权回应"；字段缺失才是"旧 server 本地解析"。
7. **planned-restart 两写一消费**：supervisor watch（supervisor.ts）、DaemonCore.stop（daemon-core.ts）写入；构造时消费并删除。
8. **autostart 采集必须先于 markUnfinishedRunsStale**（2026-07-29 起候选列表只用于记日志，但采集顺序约束本身仍然成立）。
9. **daemon 单实例**：任何启动路径（supervisor watch / 手动 / 重启）都必须保证旧实例先死——双实例 = agent 重复 spawn + scoped token 互撤（§5.4）。

## 10. 已知限制与后续方向

当前实现的已知限制：

1. ~~dispatch 并发语义是"丢弃"不是"排队"~~ **已解决（2026-07-29）**：in-flight 期间的新消息挂 promise 链串行排队，并同步推送 `agent:delivery-queued` → 前端 toast（§4.1④）。
2. **relay 模式未启用**：`generateRelaySystemPrompt` 存在但无调用路径。
3. **run store 为 JSON 文件**：已抽象 IAgentRunStore，Phase 5 计划 SQLite。
4. **仅 Claude Code / 仅 Windows / 单 daemon**：均为当前明确约束而非架构上限，演进路径（多 CLI driver 抽象、Unix 平台层、多 daemon → 托管 → 远程调度）见 `05-演进规划.md`。
5. **"沉默"与"成功"不可区分**（ecc 架构审计 2026-07-19）：回复协议只在 prompt 层强制（CLAUDE.md + REMINDER_TAIL），代码层没有"本回合是否产生过 send_message 调用"的确认。agent 读完消息不做任何回复就结束回合时，quiesce 兜底会正常判回合结束——与安静但成功的回合无法区分。如需兜底，可在 MCP send_message 调用处打点 + 回合结束时核对。
6. **MEMORY.md 无准入控制且无界增长**（同上）：agent 长期记忆完全自我写入，错误自我笔记会跨会话固化（memory poisoning）；模板要求每回合先读但没有大小上限/压缩机制，长期运行后每回合上下文成本单调上升（session resume 默认开启后有所缓解——续会话不重读，但 MEMORY 本体仍在每轮上下文里）。后续可考虑：写入前自检、按节滚动截断、或定期 compaction。

## 11. 与需求规格 §3.4 的对照

本文档描述当前实现。相对《需求规格说明书》§3.4（智能体协作体系），主要差异如下（详细接口级差异见《接口设计》§9）：

| 规格 §3.4 | 实现现状 | 性质 |
|-----------|----------|------|
| 三级智能体架构（集团中枢/子公司/渗透集群） | 扁平模型：人类与 agent 同频道协作 + 经理/worker 派发 | **结构性分歧**（产品决策：渗透分层已回退移除，平台定位转为通用协作） |
| 渗透集群不参与协作平台，仅 REST 收指令 | 所有 agent 均参与协作平台 | 结构性分歧 |
| 消息格式含 MessageType/priority/trace_id | 无 message_type/priority 字段；shared Message 有 `traceparent` 雏形 | 缺口 |
| Pub/Sub + 消息队列持久化（Kafka/Redis Streams） | PostgreSQL 落库 + WS 广播直发 | 缺口（当前单实例规模下直发够用） |
| 消息 ACK + 超时重试 + 离线熔断 | 无 ACK 机制 | 缺口 |
| 离线消息上线补拉 | agent `/receive` 游标增量拉取 | 对齐（机制不同，功能等价） |
| L1-L4 自治分级 + 超时默认行为 | 仅 action_cards 审批卡雏形，无自治分级 | 缺口 |
| 人机共融 Web UI | 已实现（人类与 agent 同界面协作、终端可观测） | 对齐 |
| 被 @ 自动获得频道可见性 | 已实现（公开频道自动入圈） | 对齐，且更精细：私有频道不自动入圈 + mentionAgents 预过滤零成本拦截 |

超规格能力（规格未覆盖，建议回写规格）：mentionAgents 预过滤、经理/worker 派发体系（dispatches）、终端观察体系（实时帧/历史日志/resize 协商）、五态生命周期管理（idle 回收/静默兜底/崩溃恢复）。
