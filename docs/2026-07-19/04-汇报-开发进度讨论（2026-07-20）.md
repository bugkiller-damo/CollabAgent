此前系统知识分散在计划文档和实施记录里（"要做什么/做了什么"），没有一份回答"系统现在长什么样"的文档。本次产出三份**以代码为准**的设计文档：22 张表、全部 REST/WS/MCP 接口、daemon 20+ 模块均从源码逐一核实。**从本次会议起，这三份文档替代口头共识，作为开发基线**——有异议当场提，会后按文档执行、按文档验收。

## 1. 智能体协作体系（01）— 20 分钟

### 走读要点

1. **体系定位**（§1）：一个 agent = 一个 Claude Code PTY 子进程；平台管路由/凭证/生命周期/可观测，AI 能力全在 Claude Code 本体。仅 Windows、仅 Claude Code（明确决策）。
2. **模块架构**（§2）：daemon-core（WS 路由）→ agent-runtime（工厂组装）→ 20+ 专责模块。两张职责表过一遍即可，不逐行讲。
3. **状态机**（§3）：五态 uninit/idle/starting/working/stopped + 迁移表。重点讲三条语义：崩溃回 idle 而非 stopped；idle→working 是 PTY 复用路径；stopped 仅显式注销。
4. **消息协作流**（§4）：@mention 时序图走一遍。重点：**mentionAgents 预过滤**（无权 agent 零 PTY 成本拦截）、daemon 侧 7 个 choke point、REMINDER_TAIL 防 /compact 遗忘、经理/worker 派发流。
5. **生命周期**（§5）：参数总表一页过；重点讲退出清理链（顺序敏感）、exit 129=idle 回收、autostart 与 planned-restart 标记。
6. **终端观察**（§6）：现场演示——面板实时画面、拖宽触发 PTY resize、Claude 收 SIGWINCH 重排。
7. **设计不变量**（§9）：8 条，逐条念——这些是 bug 修复沉淀的硬约束，评审重点是**大家是否认可并承诺遵守**。

### 评审问题（抛给大家）

- 状态机五态是否够用？要不要 error 终态？
- dispatch 并发"丢弃不排队"语义是否接受？（多人同时 @ 同一 agent 时第二条消息会丢）
- idle 回收 300s 是否合适？（此前 60s 实测会回收正在思考的 agent）

## 2. 数据架构（02）— 15 分钟

### 走读要点

1. **存储总览**（§1）：PG 主存储 + 三层内存缓存 + 可选 Redis 限流 + 磁盘附件 + daemon 文件态。无 MQ、无对象存储。
2. **22 张表**（§3）：不逐表讲，按六个域（账号/组织/协作/智能体/任务提醒/运营）扫一遍，重点讲：
   - `messages` 一表多职（消息 + 任务 + 线程），seq 全局游标
   - `channel_members` 多态（human/agent）+ is_manager 单经理部分唯一索引
   - `agent_credentials` 1:1 upsert = 重签即撤旧
   - `dispatches` 经理/worker 合同表
3. **多态无外键列**（§4）：6 个多态列放弃 FK 是有意设计，一致性靠应用层——需要大家知情认可。
4. **索引↔查询路径**（§5）：重点讲 seq 游标分页和 content_tsv 全文检索（此处有规格冲突，见议题）。
5. **缓存与失效**（§6）：session 5s 缓存的失效点清单（logout/改密/注销/吊销）。
6. **daemon 本地态**（§8）：`.slock/` 布局、safeAgentDirName 中文名哈希、daemon-state.json 两种记录。

### 评审问题

- messages 无保留策略，只增不减——接受现状还是定归档方案？
- run store（JSON 文件）是否按计划迁 SQLite？
- drizzle：schema 已有镜像但查询手写 SQL，要不要全面引入 ORM？

## 3. 接口设计（03）— 15 分钟

### 走读要点

1. **四类接口 + 认证矩阵**（§1）：REST（浏览器 cookie JWT）/ Internal（agent 用 sk_agent_）/ WS（daemon 用 sk_machine_）/ MCP（17 工具）。
2. **全局约定**（§2）：CSRF 双提交及 Bearer 豁免、限流三桶（auth 20/sensitive 5/api 100 每分钟）、seq 游标分页。
3. **REST 分域**（§3）：扫一遍即可，重点讲 messages/send 的事务边界和 mentionAgents 计算时机。
4. **Internal API**（§4）：重点讲两个设计——mint/revoke 必须账号级 token（防 scoped token 自我续期）、receive 游标单调推进（漏读即跳过，read_history 兜底）。
5. **WS 协议**（§5）：四组消息逐 type 过；broadcast 定向规则（私有频道 daemon 全发、daemon 侧自过滤）。
6. **MCP 17 工具**（§6）：表格扫一遍，说明 agent 的全部能力 = 这 17 个工具 + slock CLI。

### 评审问题

- WS 入站消息无 zod 校验——补不补？
- agent:deliver 对 daemon 全发（私有也全发）——多 daemon 前是否需要改定向？
- 发消息走 REST 不走 WS——维持还是统一？

## 4. 规格分歧与待决事项（20 分钟，逐项拍板）

### 4.1 与需求规格的 4 处明文冲突（03§9，需决定"改代码"还是"改规格"）

| # | 冲突 | 改代码成本 | 初步建议 |
|---|------|-----------|---------|
