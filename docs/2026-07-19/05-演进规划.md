# 演进规划：多 CLI / 多平台 / Daemon 服务端化

> 版本：2026-07-19 · 本文档描述**规划方向**，不是现状。现状以 01/02/03 三份设计文档为准。
> 每个方向给出：现状约束 → 目标形态 → 影响面（落到具体模块/表/接口）→ 待决策。

---

## E1. 多 CLI 支持（codex / opencode 等）

### 现状约束

agent 运行时深度绑定 Claude Code（见 01§7）：spawn 参数、就绪检测（`❯/›` 提示符正则）、忙碌标记（`esc to interrupt`）、bracketed paste 协议、terms 对话框处理、session 捕获路径（`~/.claude/projects/`）全部按 claude 调优。`command-presets.ts` 虽预留了多 CLI 参数模板结构，但只是参数表，不是驱动抽象。

### 目标形态

```
agent-runtime-spawn
      │
      ▼
 CliDriver 接口 ──┬── ClaudeDriver（现状逻辑下沉）
      │           ├── CodexDriver
      │           └── OpenCodeDriver
      │
  每 driver 提供：spawnArgs / readyPattern / busyMarker /
  pasteProtocol / termsHandler / sessionCapture / resumeArgs
```

agents 表 `runtime_profile.runtime` 字段已存在，创建 agent 时选择 CLI 类型，spawn 时按类型取 driver。

### 影响面

| 层 | 改动 |
|----|------|
| 协作体系（01） | 新增 CliDriver 抽象；`agent-runtime-spawn` 参数/就绪/paste 逻辑按 driver 分派；回合结束检测的忙碌标记按 driver 配置 |
| 数据（02） | 无表结构变更（runtime_profile JSONB 已够用） |
| 接口（03） | `POST /api/agents` 的 runtime 字段取值扩展；MCP 工具不变（agent 侧无感） |

### 待决策

- 接哪些 CLI、优先级？（建议先 codex，生态最接近）
- 不同 CLI 的 MCP 支持能力不一，降级策略（MCP 不可用 → CLI wrapper 兜底）是否可接受？
- 提示词体系（CLAUDE.md / REMINDER_TAIL）是否需要按 CLI 定制？

## E2. 多平台支持（Linux / macOS）

### 现状约束

daemon 仅 Windows（明确决策，见 01§1）：node-pty 走 ConPTY；Claude 二进制解析依赖 `.cmd` shim 提取（`agent-runtime.ts`）；CLI wrapper 主格式是 `.bat`（POSIX sh 版已生成但未经验证）。

### 目标形态

node-pty 本身跨平台（Unix 走 forkpty），主要工作是平台差异层：二进制解析（Unix 直接 `which`，无 shim）、wrapper 统一为 sh、路径/换行处理。代码中平台相关点已相对集中（shim 解析、wrapper 生成、ConPTY 参数），无架构性障碍。

### 影响面

| 层 | 改动 |
|----|------|
| 协作体系（01） | `agent-runtime.ts` shim 解析加平台分支；`setup-slock-wrapper.ts` 主格式按平台选择；测试矩阵加 Ubuntu/macOS |
| 数据（02） | 无 |
| 接口（03） | 无 |

### 待决策

- 启动时机：有 Linux 用户/服务器部署需求时启动（与 E3 服务端化天然绑定——服务器基本是 Linux，E3 落地前 E2 的 Unix 半必须完成）
- macOS 是否纳入（桌面用户场景）

## E3. Daemon 服务端化与远程调用（最大演进）

### 现状约束

daemon 跑在 **agent 所有者的本机**：一账号一条 WS 连接（`daemonClients: Map<userId, ws>`），agent:start 只推所有者 daemon，算力/凭证在 user 机器上。这意味着：用户必须自己装 daemon、机器关机 agent 就离线、无法集中运维。

### 目标形态（三个阶段）

**阶段一：多 daemon**——同一账号可注册多个 daemon（多台机器），server 侧 `daemonClients` 改多连接注册表，`agent:start/deliver` 按 agent 归属定向到具体 daemon。

**阶段二：托管 daemon**——服务端（或独立 worker 池）跑 daemon 进程，用户在 web 创建 agent 即上线，无需本机安装。agent 的 Claude Code PTY 跑在服务器沙箱里。

**阶段三：远程调用**——daemon 成为可调度资源池：按负载/归属/能力调度 agent 到合适的 daemon，支持跨节点迁移。

### 影响面

| 层 | 改动 |
|----|------|
| 协作体系（01） | daemon 注册/心跳/归属协议；agent:start 定向路由；终端观察链路不变（WS 中继天然支持远程）；**托管模式新增安全命题**：scoped token 服务端持有、PTY 需要容器/受限用户隔离、资源配额（CPU/内存/时长） |
| 数据（02） | agents 表增加部署模式/归属 daemon 字段；可能新增 daemons 注册表（id、user_id、node、capacity、last_seen） |
| 接口（03） | **WS 协议需要版本化**（规格 §4.2 本来就要求 `/ws/v1`，正好借机实施）：连接注册支持多 daemon、消息带 daemon 路由字段、agent:deliver 定向化（当前对 daemon 全发，多 daemon 下带宽浪费会放大）；新增 daemon 管理端点（注册/列表/下线） |

### 待决策

- 多 daemon 的归属模型：agent 绑定 daemon（静态）还是 server 调度（动态）？建议阶段一先静态绑定。
- 托管隔离方案：容器（Docker）/ 受限系统用户 / VM？直接决定安全评审工作量。
- 托管模式的凭证模型：scoped token 由服务端 daemon 持有，密钥管理（规格 §5.1.4）需要同步设计。
- 配额与成本：每用户/每组织 agent 并发上限、运行时长限制。
- E3 依赖 E2 的 Unix 半（服务器为 Linux），两个方向的排期需要绑定。

## 排期建议

```
E2(Unix 半) ──┐
              ├──► E3 阶段一(多 daemon) ──► E3 阶段二(托管) ──► E3 阶段三(调度)
E1(多 CLI) ───┘   （E1 与 E2/E3 无依赖，可并行）
```

- **E1** 独立可并行，收益是 agent 能力多样化，建议作为下一个迭代候选。
- **E2 Unix 半 + E3 阶段一**是托管化的前置，建议合并为一个里程碑。
- **E3 阶段二**涉及安全评审（沙箱、密钥、配额），单独立项。
